Readable data#

The inventory of every quantity readable through the read API, per object type.

Every table lists the readable attributes for one object type. dtype × lanes is the element type and tuple width; Residency is device (kDLCUDA on a DirectGPU scene, kDLCPU on CPU) or host (always kDLCPU). Quaternions are xyzw.

Per-shape columns are padded to the widest queried body’s shape count (varies per read — do not cache); read shapeCount for the real length. A shape with several materials reports only its first (material 0). On DirectGPU, disabled (eDISABLE_SIMULATION) bodies are omitted from fixed columns while discovery keeps the full count.

kinematicTargetPosition / kinematicTargetOrientation return the pending kinematic target of a kinematic body; a body with no target set (non-kinematic, or an undriven kinematic body) falls back to its current world pose. They are host-authoritative and readable on a DirectGPU scene — read position / orientation for a device-fresh pose.

isSleeping reports PhysX state when the read executes, independently of the last wake command. Use ALL scope to inspect sleeping bodies; ACTIVE is a selection of bodies that were active, not a sleep-state query. Zero velocity alone does not prove that a body is asleep.

  • On CPU and GPU scenes with CPU readback, dynamic bodies report their live state. Kinematic bodies report PhysX’s kinematic sleep state: setting a target wakes them, and they sleep after two consecutive simulation steps without a new target. Simulation-disabled bodies are included on these modes and report asleep when scene sleeping is enabled.

  • On scenes with eDISABLE_SLEEPING, including DirectGPU, every emitted value is 0 because the scene disables sleeping. This follows PhysX’s reported state even for a disabled body on a CPU/readback scene; use disableSimulation to determine whether it participates in simulation. This does not enable wake writes on DirectGPU.

  • DirectGPU keeps its existing selection rules: no groups before the first completed step, and no rows for simulation-disabled bodies. A missing row is not an awake value.

  • The host column is a read-session snapshot. Complete preceding simulation work before reading; a later step or write requires a new read to observe the changed state. Retained snapshots keep their original values under the usual read-buffer lifetime rules.

isSleeping has no point-instancer array form and is not emitted for whole-articulation, vehicle-wheel, deformable, particle or tendon queries.

Point-instancer instances read only the state attributes listed below, as an array group (one tensor per instancer, indexed by instance slot, holes zero-filled) under different names. The property and per-shape columns have no instancer form.

Character controllers#

CHARACTER_CONTROLLER has no readable columns. The controller prim is a row of RIGID_BODY position and orientation: the backing kinematic actor’s global pose. That orientation includes the capsule-axis rotation and is not the fixup-corrected orientation written back to the prim. move updates the controller and its kinematic target immediately; that rigid-body pose changes on the next simulation step, when the target is integrated.

SDF shapes#

SDF_SHAPE has no readable columns. Evaluate the shapes’ signed distance fields at your own points with ovphysx_evaluate_sdf_shapes; see SDF shapes.

Root state and centerOfMassWorld are in scene-world coordinates; centerOfMassLocal is in the root link’s COM frame — place it in the world with the root’s mass-frame pose, not its actor/prim pose (the two differ when the root has a non-identity mass pose).

The six int32 topology scalars — dofCount, linkCount, jointCount, fixedTendonCount, spatialTendonCount and isFixedBase — replace the deprecated ovphysx_get_articulation_metadata field-for-field. They are host-resident on every device like shapeCount (read from host-side articulation state, so no device copy is needed) and emitted in the one scene-wide group even when base type varies per row. isFixedBase reflects the live base flag, so a runtime setArticulationFlag(eFIX_BASE, …) toggle is visible on the next read. The tendon counts are per articulation, not the view-wide maxima the deprecated getter reported; linkCount counts articulation links (the old struct’s mislabelled body_count), not standalone rigid bodies; and isFixedBase is an int32 0/1 flag. The dofJointPath / dofAxisIndex descriptor is the non-binding successor to the DOF / body / joint name lists: each is a padded per-DOF array (host-resident, one row per articulation, in cache-DOF order) that maps inverse-dynamics column (isFixedBase ? 0 : 6) + k to its owning joint prim — an interned prim-path handle, resolved through the attached Stage’s path dictionary like prims.list (0 pads) — and to that DOF’s ordinal among the joint’s unlocked axes. Link and joint names are then the leaf of the kOvxArticulationLink / kOvxArticulationJoint prim read by ovphysx_read. Limitation: only DOF-bearing joints appear — a fully-locked (zero-DOF) joint has no read group or descriptor entry, so its name/path is not recoverable through the read API; the deprecated ovphysx_articulation_get_joint_names still lists those fixed joints.

Note. A group’s tuple width is a 16-bit field, so a single inverse dynamics column wider than 65 535 (roughly a 64-link / 189-DOF articulation’s Jacobian, or a mass matrix past M ≈ 256) is omitted for that cohort. The read succeeds, other supported columns remain available, and the optional summary reports OVPHYSX_READ_OMISSION_UNSUPPORTED_CONFIGURATION for the affected request.

Articulation joints — DOFs#

Articulation joints (ARTICULATION_JOINT) emit an array group with one tensor per joint prim. Each tensor has one row per unlocked axis, in PxArticulationAxis order — one value per row (dtype.lanes is 1), except jointLimit, whose row is the (low, high) pair (dtype.lanes is 2). Don’t confuse the axis count (the tensor’s shape) with lanes. A read may ask for state, control, or properties in any combination. Rotational axes carry the joint’s body-order sign; angular DOF quantities are in degrees (as USD-authored).

Note. A requested attribute produces one array group whose tensors[i] holds joint i’s axis values — not one group per joint. Code that reads tensors[0] and advances to the next group sees only the first joint, and does so silently on a single-joint scene.

jointLimit is reported as the authored (lower, upper) pair, in order, regardless of the joint’s body order — unlike jointPosition, which negates when body0 is the child.

jointProjectedForce and linkIncomingJointForce (on articulation links) are computed per read rather than gathered from stored state, so each costs several times a four-column pose/velocity read of the same prims — request them in the read that needs them, not in a per-step pose read. jointProjectedForce uses the same one-row-per-unlocked-axis shape as the other joint columns: a locked axis is omitted (not a zero-filled row), and a fixed joint — which has no DOF — contributes no row.

Gear indices use -1 for reverse, 0 for neutral and positive values for forward gears. Before a recorded automatic shift, autoboxTimeSinceLastShift can hold the native float32-maximum sentinel instead of an elapsed duration. The readable controls use the same names as writes. An unconfigured brake channel reads zero; writing it has no effect. requestedGear, tank thrust0 / thrust1, and resetToRestState are write-only. targetGear reports the transmission’s internal state, not an echo of requestedGear.

Discovery lists readable attributes supported by at least one selected vehicle. Mixed reads emit only applicable rows, with UNSUPPORTED_CONFIGURATION in the optional session summary for omitted vehicles. Always use each group’s prim list: a Standard-only column can have fewer rows than a control column. A disabled vehicle remains in ALL membership.

All these columns are read-only. The existing raw-wheel driveTorque, brakeTorque and steerAngle controls are write-only; wheelSteerAngle is actual telemetry, separate from that steering command.

isOnGround == 0 means no valid current contact sample. It does not prove that a sleeping vehicle is physically airborne. Adding or removing any runtime object record in the owning attachment invalidates contact data until the next completed vehicle update, even when the changed object is unrelated to that contact. Before the first update and for sleeping or disabled vehicles, contact data can also be invalid. In that case groundPlane, groundHitPosition and all three ground identities are zero. A ground identity is an ovx_primpath_t represented as uint64. Resolve it with the attached Stage’s path dictionary, exactly as a group’s prim identities. Zero means absent or unrepresentable, including an implicit default material. These values are not pointers or private object IDs. Length, force and torque follow the stage’s units.

Debug render#

Debug render (DEBUG_RENDER) is one instance-level target, not a prim. A query does not require an attached stage. Settings are one row. Geometry columns are a snapshot of PhysX debug primitives for scenes whose attach handle matches this instance. Position index i and color index i are the same primitive. Shape 0 is an empty list. Host-only always.

Geometry timing. Complete simulation before reading. On CPU scenes, PhysX actor/shape wireframes use poses from the start of each scene’s latest simulation step, before integration. With substepping, this is the start of that scene’s last substep. Contact and friction primitives describe contacts computed for that step. Reading copies the existing primitives; a moving body’s wireframe can therefore trail its rendered post-step pose. The simulated body state is not delayed.

Contact sensors#

Contact sensors (CONTACT_SENSOR) include rigid bodies and articulation links carrying PhysxContactReportAPI, and every link of an articulation carrying it. On CPU simulation and GPU dynamics with CPU readback, each collider carrying the schema is also a sensor. A body row aggregates all of its shapes’ contacts and each collider row reads only its own shape’s, so the two overlap: do not sum net forces or count contacts/events across a body and its own colliders, or they double-count. Collider rows are host-only — a DirectGPU scene enumerates only reporting bodies (a selection naming only a separate child collider discovers no rows there). Every attribute is read-only and describes the last step; each scene’s sensors come back as their own groups, reduced with that scene’s step dt. Three query forms select them — the whole set (ovphysx_query), a prim-set selection (ovphysx_query_selection; pattern= / prim_paths= in Python), and a contact query that pairs each sensor with F filter bodies. ACTIVE scope behaves as ALL.

Child collider sensors#

On CPU simulation and GPU dynamics with CPU readback, a child collider can be selected as a contact sensor when PhysxContactReportAPI is applied to that collider. This makes the sensor available; it does not by itself enable contact reporting for its owning rigid body.

To enable reporting from that body, also apply PhysxContactReportAPI to the owning rigid-body prim. For an articulation, reporting can be enabled on the owning link or on the articulation root, which enables reporting for every link. A child sensor can also receive contacts reported by the other actor in the pair. If neither actor reports matching contacts, the child remains a valid sensor but reads zero force, even while touching another object.

For example, add this authoring fragment at the stage root and select /Body/Collider to read that shape’s contacts:

def Xform "Body" (
    prepend apiSchemas = ["PhysicsRigidBodyAPI", "PhysxContactReportAPI"]
)
{
    float physxContactReport:threshold = 0

    def Cube "Collider" (
        prepend apiSchemas = ["PhysicsCollisionAPI", "PhysxContactReportAPI"]
    )
    {
        double size = 0.5
    }
}

Configure reporting settings, including physxContactReport:threshold and physxContactReport:reportPairs, on the reporting body, link, or articulation root. Settings on a separate child collider do not configure its owner’s reporting. The example enables reporting from /Body without depending on the other actor; sleeping and other reporting conditions still apply.

Deprecated contact bindings. On CPU simulation and GPU dynamics with CPU readback, selecting the owning body as a sensor in the same binding or another live contact binding on the same attachment credits the contacts to the body and leaves the child sensor at zero. Wildcard patterns can select both. For a child binding, enable reporting on /Body but select only /Body/Collider as a sensor, and establish the bindings before stepping. Session contact reads support body and child rows together; see the Contact Binding tutorial for the binding limitations.

A standalone static collider is its own rigid actor, so applying the schema to that prim enables reporting directly on CPU simulation and GPU dynamics with CPU readback. On DirectGPU, a standalone static collider remains a sensor row but reads zero force. DirectGPU session queries omit separate child-collider rows; select a dynamic body or articulation link to read forces instead.

Reading contact data#

Sleeping contacts. On CPU and GPU-dynamics scenes with CPU readback, persistent contacts stop being reported when neither body in the pair is active. A settled sensor can therefore have zero forces and no contact arrays while still touching the ground. This also applies to contact bindings; environment IDs do not disable contact reporting. DirectGPU disables sleeping, so its contact tensors can remain nonzero on the same settled scene. For continuous reporting, disable sleeping before attachment (for example, physxScene:disableSleeping = true on a scene with PhysxSceneAPI), or wake the bodies and complete another simulation step before reading. Use isSleeping to inspect sleep state.

On a DirectGPU scene a sensor or a filter that is a point-instancer prototype stands for its first instance only, as in the contact binding: every column reads that instance’s contacts, where a CPU scene reads every instance’s. Another sensor’s contacts with each instance are unaffected.

A sensor’s points (anchors) are concatenated in event order; contactEventPointCount (contactEventAnchorCount), one value per event, splits them per event. A sensor has an array when it has at least one element at the attribute’s level this step, so a sensor whose only event is a lost pair, which carries no point, has event arrays but no point or anchor array. Event values are as reported: impulses, not forces, never negated.

How to read these values:

  • Force sign. A force is the one the sensor receives: a point’s normal force is its impulse divided by dt — the impulse’s magnitude on a CPU scene, the solver’s normal impulse on a DirectGPU scene — negated when the sensor is the pair’s second body, and normals are never flipped. So force × normal is the force on the sensor.

  • Identities are prim-path handles interned in the attached Stage’s dictionary; obtain it through stage->vtable->get_path_dictionary(stage->context) in C and resolve through the ovx path-dictionary API, or use ovstage.PathDictionary.path_to_string in Python. An identity with no prim reads 0.

  • Exact sizing. Each array holds the step’s elements — no capacity, no truncation. A sensor with no element this step is absent from an array group, and the group is absent when no sensor has one.

  • Order. On a CPU scene a sensor’s elements keep report order (within a filter column for the filtered detail); on a DirectGPU scene their order is unspecified, as it is in the contact binding.

  • DirectGPU. The filtered detail’s arrays and the raw contacts synchronize the host once per read, to size them from the per-sensor counts; a read that asks for none of them does not, nor does one of the count columns alone. Events are not served (PhysX’s GPU contact pairs carry no event type): the read completes without them. Before the first step the fixed columns read zero and the arrays are absent.
