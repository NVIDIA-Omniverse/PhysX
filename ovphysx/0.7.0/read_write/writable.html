Writable data#

The inventory of every quantity writable through the write API, per object type. Read-only quantities are covered in Readable data; this page lists only what a write accepts.

Every table gives, per attribute, its Meaning, dtype × lanes (element type and tuple width), and — where it applies — Frame and Units. Quaternions are xyzw. A (write-only) tag marks a control that is not readable (no read-back); its persistence varies (see Write timing, ordering, and persistence). Column residency follows the read: device on DirectGPU, host on CPU — except joint DOF properties and particle points/velocities, which are host-staged on every scene.

Writability classes#

To ask programmatically whether an (object type, attribute) pair is accepted:

  • In C: ovphysx_writability(object_type, attribute, &out)

  • In Python: from ovphysx._bindings import writability, then writability(object_type, attribute). This helper currently lives in the private bindings module; it is not exported as ovphysx.writability or PhysX.writability.

It reports one of five classes — OVPHYSX_WRITABILITY_<NAME> in C (ovphysx_writability_t), the matching integer in Python:

Value

Class

Meaning

0

UNCLASSIFIED

the type does not accept this name; a write rejects it

1

WRITABLE

writable, no precondition beyond the object existing

2

CONDITIONAL

writable only under a stated condition; if unmet the write reports it and writes nothing (does not partially apply)

3

a control input; writable but not readable (no read-back). Whether it clears each step or persists is a separate per-attribute property (see persistence, below)

4

READ_ONLY

readable only; writing is an error naming the type, not a silent no-op

The query is scene-independent (a hand-maintained snapshot of the runtime tables; string keys only; the object type is bounds-checked). It classifies the attribute, not the object’s current state. Opening a write session remains the authoritative check for a live scene; the optional write summary reports planned groups, not writability.

Write timing, ordering, and persistence#

  • Never auto-warmed. The session write never steps for you. On CPU and on GPU with readback, a write before the scene’s first step commits and is applied. On DirectGPU (suppressReadback / eENABLE_DIRECT_GPU_API), that same pre-step commit is refused until a first step has sized the GPU view. Call ovphysx_warmup / step_sync first for a recipe that works on every mode. See data model — DirectGPU.

  • Applied at commit, into live PhysX — not deferred to the next step. A written value is observable through a read (or the borrowed physxPointer address) before the next step. Character-controller move updates its controller at commit, but the backing actor’s rigid-body pose is updated on the next step. The write_done_sync you pass (cuda_stream= / cuda_wait_event= in Python) orders the commit after your fill’s CUDA stream/event; see CUDA synchronization. The write runtime separately synchronizes commit with an outstanding PhysX step. Keep session and step calls serialized and complete a mid-session step before further scene-dependent accesses; this internal synchronization does not collect the step’s outcome.

  • Read-modify-write for split poses. Writing position pre-reads and preserves orientation (and vice versa), because they are two slices of one atomic transform. Linear and angular velocity are independent (no pre-read). Particle/deformable point writes preserve the .w inverse-mass lane.

  • What the sim overwrites. State (poses, velocities, root state, joint DOF state, point sets) is recomputed by the next solver step. Inputs, targets, and properties (drive targets, all joint and tendon properties, materials, mass/inertia/COM, flags) persist across steps until re-written. Rigid external forces (force, wrench) are the only write-only controls the solver consumes and clears each step. Vehicle wheel commands (driveTorque, brakeTorque, steerAngle) are also write-only but persist until re-written — the solver reads them every step without clearing, so a one-step command keeps applying until the caller resets it (write 0). Whole-vehicle controls also persist. resetToRestState instead runs once at commit and is never retained as a per-step command. Character controller move is applied once at commit and is not replayed; see its section below.

  • Persistence is runtime-only. Every write publishes into live PhysX simulation state. No write is authored back into the ovstage / USD source representation. (A read gathers from the same live state, which is why a written value round-trips through a read.) Propagating results back into ovstage is a separate output-drain direction, not this write path — and its coverage differs from the writability query (see the last item in Known limitations).

  • Several attributes per session. A write session opens over an attribute array and validates all of it before exposing a group: an unsupported, read-only or duplicate name fails the open and publishes nothing. Each fetched group names its attribute through attribute_index, the position in that array (see Session results). Commits run in the order the caller issues them, whatever the fetch order; independent attributes are not promised to commute.

  • No fill mask. A commit publishes the whole mapped group — every object the query selects. To write a subset of prims, open the query with a prim-set selection (explicit prim handles or a path pattern); the write then maps only the selected prims. See Selecting a subset of prims. There is no per-row mask inside a group. Neither ALL nor ACTIVE scope is a kinematic-body filter. Rows are re-resolved at every commit, never cached across sessions or steps.

  • Committing a live group consumes it. After an accepted commit of a live group owned by this session – ovphysx_commit_group in C, session.commit(group) in Python – the mapped buffers belong to physics (dereferencing the C pointers, or touching the Python tensor views, is undefined) and commit is not idempotent. A group left uncommitted when the session is released (or the Python with block exits) is discarded, not published. Detach and instance destruction also invalidate write sessions; finish external consumers of their buffers before these transitions.

  • Read the failure reason. Python raises RuntimeError for a rejected submission and TaskError (a RuntimeError) with the write’s diagnostic when an operation is waited. In C, admission rejection uses ovphysx_get_last_error() on the calling thread; accepted execution failures are reported by the wait and ovphysx_get_last_task_error(). Read the cause before destroying its wait result. A rejected submission retains the group. Once execution accepts this session’s live group for publication, it is spent even if publication fails. An unknown, foreign or already-spent group reports a task failure without consuming another valid group. Previously committed groups remain applied, and the failing group may also be partially applied. There is no rollback or applied/rejected row count; a failure guarantees zero writes only when its diagnostic says so.

Rigid bodies#

Rigid bodies (RIGID_BODY): all rigid state and authored inputs are writable; derived quantities (linearAcceleration, angularAcceleration, inverseMass, inverseInertia, shapeCount) and the reported isSleeping state are read-only.

On CPU and GPU-with-readback scenes, PhysX rejects linearVelocity and angularVelocity setters on standalone kinematic bodies. Commit reports the SDK error, but valid dynamic rows in the same group can still be written, including rows after the rejected body. The kinematic body’s velocity stays unchanged. This SDK restriction does not apply to DirectGPU velocity writes.

Point-instancer instances are written in the same session as array groups (position / orientation local, velocities world). On DirectGPU an instancer group holding a disabled instance is refused as a whole (writes nothing) — asymmetric with standalone bodies, whose disabled rows are silently filtered.

Writing disableSimulation retains disabled rows in the group, so writing 0 re-enables a body. This disables a standalone body only — a point-instancer instance cannot be disabled individually (disableSimulation is not an instancer-writable column and there is no per-instance route), which is unsupported in this release. Do not toggle eDISABLE_SIMULATION directly on a PxRigidDynamic* read from physxPointer — ovphysx does not observe the change, and on a DirectGPU scene the next read or write may resolve a stale GPU index to the wrong body without error. Write disableSimulation through the write API instead.

kinematicTargetPosition / kinematicTargetOrientation are CONDITIONAL: supported on CPU scenes and GPU scenes with CPU readback. They drive a kinematic rigid body to a world pose; the write is refused outright on a DirectGPU scene because PhysX never uploads the CPU-integrated target to the device. Direct position / orientation writes are device-backed on DirectGPU, but teleport the body without a kinematic target’s step velocity; they are not an equivalent way to carry a resting load. Preconditions are enforced atomically: a disabled kinematic body, or a non-finite position or a non-finite/zero quaternion, fails the whole commit naming the body. A non-kinematic body cannot be driven, but the session still opens and its other rows land — that body is warned and skipped, not name-refused. Position and orientation are one transform, so writing one preserves the other.

wake is a write-only command. Read isSleeping separately to observe the current state; it does not echo the command. Nonzero wakes the addressed rigid dynamics, zero sleeps them, per prim in one commit. It is a one-time command over the whole mapped group: every row is driven, so a zero row actively sleeps that body and there is no leave-unchanged value or per-row mask. Use a prim-set selection to map only the bodies you mean to toggle, including sleeping bodies; unselected bodies stay untouched. It is CONDITIONAL, refused only on a DirectGPU scene (eENABLE_DIRECT_GPU_API), because DirectGPU requires eDISABLE_SLEEPING. The command is supported on CPU scenes and GPU scenes with CPU readback. Non-dynamic, kinematic, and disabled bodies are skipped rather than driven, and on an eDISABLE_SLEEPING scene the sleep half (wake == 0) is a no-op.

The per-shape material attributes (staticFriction / dynamicFriction / restitution) are carried by a PxMaterial that several shapes may share (the authored default). Writing one gives the written shape its own material, so the write is isolated — a sibling shape still bound to the original material is unchanged. Other material settings, including compliant-contact acceleration mode, remain unchanged. The trade-off: once a shape owns its material, a later edit to the originally-authored material (an ovstage / USD material change) no longer reaches that shape; only shapes still bound to the authored material follow. The fork has no authored material identity: contact-point material handles report the scene’s default material prim when one is authored, or 0 otherwise.

All whole-vehicle controls are CONDITIONAL in ovphysx_writability, including the write-only gear, thrust and reset commands: drive subtype or chassis state can refuse them. Opening the write checks every selected vehicle and rejects incompatible rows. A mixed selection cannot silently skip unsupported vehicles. At commit, every addressed vehicle and value is validated before any setter runs. An invalid value leaves this entire group unchanged.

An unconfigured brake channel accepts a write with no effect and reads zero. On DriveBasic, accepted negative / zero / positive gear requests select reverse / neutral / forward; 255 is positive and therefore selects forward. On DriveStandard, 255 selects automatic control when an autobox is configured. Without an autobox the request is accepted with a warning, and automaticTransmission remains zero. Requests for unconfigured forward gears have no effect. A successful request is not a promise that currentGear or the internal targetGear immediately becomes that value. These controls persist until replaced.

Reset ordering#

resetToRestState resets each row containing 1 once when its group is committed. It is never replayed on later steps. A zero row makes no mutation but still undergoes target eligibility checks. Releasing a filled group without committing does nothing. The normal single-commit rule prevents executing the same group twice.

Reset preserves chassis pose and existing controls. It clears chassis velocity and accumulated forces, resets wheel dynamics, finishes a pending gear change at its internal target and restores the configured engine idle speed. It is not a restoration of the originally authored scene. A disabled vehicle controller can be reset, but any addressed chassis with disableSimulation set rejects the group before mutation, including a row whose reset value is zero. Use the chassis isSleeping read when the current sleep state matters.

Commits execute in caller order and are not a transaction. For a new driving episode, commit reset first, then the desired chassis pose and velocity, then the desired controls. Resetting after a velocity write intentionally clears that velocity. Preserved throttle can move the vehicle again on its next step; write zero if that is not desired.

Character controllers#

CHARACTER_CONTROLLER accepts one host column, move. It is CONDITIONAL: refused on a DirectGPU scene (eENABLE_DIRECT_GPU_API), because PxController::move updates the proxy through setKinematicTarget and that CPU target is not uploaded. Pose is the controller prim’s RIGID_BODY position and orientation: the backing actor’s global pose. That orientation includes the capsule-axis rotation and is not the fixup-corrected orientation written back to the prim.

Deformable volumes / surfaces#

Deformable volumes / surfaces (DEFORMABLE_VOLUME, DEFORMABLE_SURFACE) are GPU-only, device-resident. restPoints and the connectivity indices are read-only. kinematicTarget (volume only) drives sim-mesh nodes to a target through a runtime-owned per-body buffer whose lifetime outlives any single write — so, unlike a freed-at-release write column, the solver keeps reading valid memory. It is CONDITIONAL: refused on a volume already made kinematic another way (eKINEMATIC / kinematicBody, or a tensor-binding view’s ePARTIALLY_KINEMATIC), and driving is monotonic — a write cannot return an already-driven node to free (no un-pinning). Per node, the .w lane selects whether it is driven, with inverted polarity: w == 0 drives the node to its xyz target, w != 0 leaves it free.

Debug render#

Debug render (DEBUG_RENDER) settings are writable without an attached stage. Geometry columns (pointPosition / pointColor, linePosition / lineColor, trianglePosition / triangleColor) are read-only. A commit pushes the instance’s full settings onto scenes of this attach; a parameter value of 0 turns that parameter off. A scope write is uint64 shape [4097]: element 0 is the count (at most 4096) and elements 1..count are the path tokens. Count 0 draws everything. A cullingBox write is float32 shape [7]: element 0 is 1 to store the next six floats (min xyz, max xyz, min ≤ max), or 0 to clear the box. Scope tokens are cleared on detach because they belong to the stage path dictionary.
